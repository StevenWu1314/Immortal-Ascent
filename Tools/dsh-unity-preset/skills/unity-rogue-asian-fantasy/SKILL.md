# Rogue Asian Fantasy — project coding reference

Turn-based 2D roguelike dungeon crawler. Unity **2022.3.62f2**, URP 14, 2D feature
set, Tilemap, TextMeshPro, UGUI, and the legacy `Input` API.

~6,400 lines of plain C# in 42 files under `Assets/Scripts`, in the default
`Assembly-CSharp` assembly with **no namespaces** and **no `.asmdef`**. Only
`Assets/TextMesh Pro` ships its own assemblies, and that is vendored third-party code.
`Assets/Resources` holds content only (no scripts).

`Docs/Refactoring-Plan.md` is the current ponytail-audit plan for this repo (the
codebase has already been through one cleanup pass). Read it before proposing large
deletions so you neither redo its work nor contradict it.

## Do not edit these

| Path | Why |
| --- | --- |
| `*.unity`, `*.prefab`, `*.asset`, `*.controller`, `*.anim` | Unity-editor-authored YAML. Hand-editing corrupts GUID/fileID references. |
| `*.meta` | Unity owns sidecar metadata and GUIDs. Never create, edit, or delete one by hand. |
| `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/` | Generated. Gitignored scratch. |
| `*.csproj`, `*.sln` | Regenerated by Unity / IDE integration. |
| `Assets/TextMesh Pro/` | Vendored package. Treat as read-only; changes are lost on reimport. `Assets/Scenes/ui.unity` renders with `Assets/TextMesh Pro/Examples & Extras/Resources/Fonts & Materials/Electronic Highway Sign SDF.asset`, so the `Examples & Extras` folder cannot be deleted wholesale without first relocating that font. |
| `Packages/com.nuskey.unity-agent-client/`, `Assets/Plugins/UnityAgentClient/` | Local ACP/MCP editor tooling. **Untracked and not gitignored**, so `git add -A` would commit them into the game repo. Stage files by name. |

When a task genuinely needs scene, prefab, or inspector wiring (a new serialized
field to fill in, a list to populate, a component to add), finish the complete C#
side and then hand the user a short, explicit editor checklist — or write a
`[MenuItem]` editor script that performs the wiring through `SerializedObject` (the
pattern in `Assets/Scripts/Item/Editor/ChestSetup.cs`) and let the user run it.
`Assets/Scripts/Level Generator/Editor/MapgenDiagnostics.cs` is the reference for a
`[MenuItem]` that only asserts and logs. Do not attempt the wiring yourself by
editing YAML.

**Never rename or retype an existing serialized field** (`public` fields and
`[SerializeField]` privates) without telling the user. Their values are stored in
scenes and prefabs keyed by field name; renaming silently resets the data to
default and is very hard to notice.

## Runtime contracts

These are the shared invariants the whole game relies on. Read the call sites
before changing any of them.

### 1. The grid is terrain only; entities are separate

`Grid` (`Assets/Scripts/GameGrid/Grid.cs`) stores **terrain codes** in an
`int[width, height]`. `RoomFirstDungeonGenerator.EnsureGrid()` is the single owner and
publishes it as `Grid.Current`; everything else must read `Grid.Current` rather than
building or searching for its own instance.

Terrain codes:

| Code | Meaning | Walkable |
| --- | --- | --- |
| `0` | floor / wall-free corridor | yes |
| `1` | wall, water, **and out of bounds** | no |
| `99` | unopened chest (`LevelValidation.ChestCode`) | no |
| `2` | deep water | no — **legacy, nothing writes it any more** |
| `3` | enemy | no — **legacy; its only reader, `Grid.detectEnemiesInALine`, was deleted** |
| `5` | bridge | yes — **legacy, nothing writes it, but `IsWalkableTerrain` still accepts it** |

Only `0`, `1` and `99` are written by current code.

`Grid.IsWalkableTerrain(int)` and `Grid.CellFromWorld(Vector3)` are the single
definitions of "can an entity stand here" and "which cell is this". Route new
movement, pathfinding, and generation checks through them instead of comparing
codes inline — that is how the map edge stays blocking (`Grid.OutOfBounds == 1`,
which is deliberately non-walkable).

**Entity occupancy is not in `Grid`.** `EntityManager` owns a
`Dictionary<Vector2Int, GameObject>` with a one-entity-per-cell rule, and moving
into an occupied cell is what triggers melee combat. When adding a new moving
entity you must register, move, and unregister it through `EntityManager`, or
collision and combat will silently ignore it.

Cells are derived with `Mathf.FloorToInt` on world X/Y (cell size 1, origin
`(0,0)` in practice), so keep entity positions on integer coordinates.

**Chests change terrain at runtime.** `TilePlacer.generateLootTiles` writes `99`, and
`Chest.Open` turns the cell back into passable floor. That takes **two** writes, and
both are required:

```csharp
Grid.Current.SetValueAtLocation(cell.x, cell.y, 0);   // the movement authority
IslandManager.MarkWalkable(cell);                     // the island map's snapshot
```

Doing only the grid write leaves the cell `Unassigned` in the island map, which both
makes `IslandManager.CanMoveTo` keep refusing the step while the room has enemies and
makes `IslandManager.CountLivingEnemies` miss an enemy standing there (so the room can
read as cleared while one is still alive). `MapgenDiagnostics.ChestWalkability` asserts
this, including a negative control.

### 2. Turn order flows through a static event

The turn pipeline is:

1. `Controls` (player) resolves the player action and raises
   `Controls.onMoveEvent`.
2. `TurnManager.callTaketurn` receives it, alerts enemies in the player's room,
   and starts the `TakeTurns` coroutine.
3. The coroutine dequeues each `EnemyBehavior` and calls `takeTurn()` with a
   small delay, then clears `Controls.takingTurn` in a `finally` block.

`Controls.takingTurn` is the player-input lock. Anything that consumes a turn
must set it and raise `onMoveEvent` **after** the action resolves, or the player
will act again while enemies are still moving. `TurnManager` subscribes in
`Start` and unsubscribes in `OnDestroy`; new `static event` subscriptions must be
symmetric the same way, because these are static channels that survive scene
reloads and leak handlers otherwise.

`EnemyBehavior` reads `Grid.Current` rather than searching for a generator, and owns a
lazy `HomeIsland` resolved from `IslandManager`.

### 3. IslandManager is a static snapshot, not a singleton

`IslandManager` (`Assets/Scripts/Managers/IslandManager.cs`) is a `static class`, and it is
the exit gate: the player may not leave a room that still holds enemies. It is built
once per generation by `RoomFirstDungeonGenerator.generateBranchingDungeon()` calling
`Rebuild(roomsSpace)`.

Two things follow, and both bite:

- **`Rebuild` snapshots walkability.** Anything that becomes walkable later must be
  re-tagged through `MarkWalkable`. See the chest note above.
- **`CountLivingEnemies` counts by island id**, walking `EntityManager.AllEntities`.
  A cell that is walkable but `Unassigned` therefore hides whatever stands on it.

`IsPartOfRoom` is what keeps enemies inside their own room (it uses the room rectangles,
not the id map), while `CanMoveTo` uses the id map. `Unassigned == -1`, `Passage == 0`,
room ids start at 1.

### 4. Managers are scene-local singletons

`TurnManager`, `EntityManager`, `PlayerStats`, `Inventory`, `Equipments`, `LootGen`,
`UIManager`, `CraftingManager` and `InscriptionPanel` expose a `static Instance` and
guard it in `Awake` with a destroy-the-duplicate check. The project-wide convention is
`public static X Instance;`, assigned in `Awake` — match that instead of introducing a
new pattern. Prefer `Grid.Current`, `IslandManager` and the existing `Instance`
accessors over `FindObjectOfType` in gameplay code.

### 5. Items, and where crafting lives

`ItemDefinition` (`Assets/Scripts/Item/ItemDefinition.cs`) is an immutable shared asset and the
single source of truth for what an item *is*: identity, stacking, kind, weapon/armor
numbers, consumable effect, inscription effect, and — since the crafting rework — the
optional `recipe` list.

- **An empty `recipe` means "not craftable".** There is no separate `Recipe` asset type
  any more; `Recipe.cs`, `Recipies.txt`, the two `Recipe` assets and both crafting
  custom editors were deleted.
- `IsCraftable` / `CanCraft()` / `Craft()` live on the definition; `Craft()` validates the
  whole recipe and `hasRoomFor()` **before** removing anything.
- **Item definitions must stay under `Assets/Resources/ItemDefinitions/`.**
  `CraftingManager.LoadAvailableRecipies()` finds them with
  `Resources.LoadAll<ItemDefinition>("ItemDefinitions")`; move them out of a `Resources`
  folder and the crafting panel silently shows nothing.
- New content is created from `Assets > Create > ScriptableObjects > Item Definition`.
  The old `PCG/DungeonSpecifications` menu is gone with that class.

Per-item state (inscriptions) lives in `EquipmentInstance`, carried by `ItemStack.instance`;
equipment never stacks. `CraftingManager.CraftingPanel.transform.Find("itemholder")` is a
name-based lookup into the scene's crafting panel.

### 6. A lot of the scene wiring is looked up by name

There is no dependency injection here: several components find their collaborators with
`GameObject.Find` / `FindWithTag` / `transform.Find` at `Start`/`OnEnable`. Renaming or
re-parenting any of these objects in the scene silently disables the feature (most of the
lookups are null-guarded, so they fail quietly rather than throwing):

| Looked up | By |
| --- | --- |
| `UIManager` | `Enemy.OnEnable`, `Inventory.Start` |
| `UIManager/Inventory/itemholder` | `Inventory.Start` (the fixed inventory slots) |
| `CurrentPos` | `Controls.Start` (the position readout) |
| `HpBar`, `ExpBar` | `PlayerStats.OnEnable` |
| `Collidable Plants` (a Tilemap) | `RangeAttackTilemap.Start`, `RangeEnemyBehavior.Start` |
| `Level Up UI` | `UIManager.toggleLevelUpMenu` |
| `str`, `dex`, `health` | `levelUpUI.OnEnable` (the level-up buttons) |
| `slot` → `Item` | `ItemBox.EnsureImage` |
| the `Player` **tag** | `EnemyBehavior.Start`, `UIManager.CloseMenu` |

Enemy prefabs also carry the `Enemy` tag, which the generator uses to sweep old enemies
before regenerating.

## Coding conventions in this codebase

Match the file you are editing. This project is mid-development, so its style is
inconsistent; consistency with the surrounding file beats a global standard.

- No namespaces. `public class Foo : MonoBehaviour` at file scope.
- `MonoBehaviour` lifecycle methods are mostly `private` by convention; many are
  `void Start()` / `void Update()` with no modifier. Either is fine locally.
- Fields that designers tune are `public` or `[SerializeField] private`. Runtime
  state is `private`/`internal`.
- Coroutines (`IEnumerator` + `StartCoroutine`) drive sequenced gameplay timing
  rather than `async`/`await`, which Unity's older runtime here does not support
  well.
- Spatial queries use `Vector2Int` cells plus `Grid`/`EntityManager`, not raycasts.
- `Debug.Log` is used liberally, including in hot paths and turn loops. Keep it
  sparse in new code and prefer `Debug.LogWarning`/`LogError` for real faults.
- XML `<summary>` doc comments appear on the newer grid and entity APIs. Add them
  to new public APIs; do not retrofit the older files.
- Tabs vs spaces: files use 4 spaces. `.editorconfig` is absent, so copy the file.

## Verification

There is no unit-test suite. Verify in this order, cheapest first, and report
exactly which step you ran.

**1. Compile check (do this for every C# change).** This imports scripts and
reports compiler errors without a run loop. Use the project's exact editor:

```bash
pgrep -fl "Unity.app/Contents/MacOS/Unity" | grep -v batchmode   # is the editor holding the lock?
"/Applications/Unity/Hub/Editor/2022.3.62f2/Unity.app/Contents/MacOS/Unity" \
  -batchmode -nographics -quit \
  -projectPath "/Users/stevenwu/Documents/GitHub/Rogue Asian Fantasy" \
  -logFile - 2>&1 | grep -E "error CS|Compilation failed|Scripts have compiler errors"
```

The user usually has this project open, and **batchmode cannot share it**. Two
instances cannot hold the same project, so the command aborts with `It looks like
another Unity instance is running with this project open` and exit code **134**
(SIGABRT). If that happens, do **not** kill the editor — that risks unsaved scene
work. Instead pick one of:

- the open editor already compiled your change: check
  `~/Library/Logs/Unity/Editor.log` for `error CS`, and confirm the matching assembly is
  newer than every `.cs` you touched — `Assembly-CSharp.dll` for runtime code,
  `Assembly-CSharp-Editor.dll` for anything under an `Editor/` folder:
  `find Assets -name '*.cs' -newer Library/ScriptAssemblies/Assembly-CSharp-Editor.dll`;
- fall back to step 1b and say that you did;
- ask the user to close the editor.

Two traps: the batched editor **exits `0` even when scripts fail to compile** — read
the log, not the exit code; and it rewrites `Library/`, which is gitignored. Confirm
afterwards that no tracked file changed unexpectedly:

```bash
git status --porcelain -- Assets ProjectSettings
```

**1b. Fallback when the editor is open (weaker signal).** A Roslyn build catches
syntax and type errors against the last import, but not scripts Unity has not imported
yet:

```bash
dotnet build "Assembly-CSharp.csproj" -nologo -v q 2>&1 | grep -E "error CS" | head -40
```

`dotnet` 9 is installed system-wide. The generated `.csproj` lists its sources
explicitly, so after **adding, deleting, moving or renaming a `.cs`** you must prune
stale `<Compile Include>` entries (or let the editor regenerate the file) or the build
reports files that no longer exist. Treat this as weaker than the real editor check and
say which one you ran.

**2. Headless logic checks.** `MapgenDiagnostics`
(`Assets/Scripts/Level Generator/Editor/MapgenDiagnostics.cs`) holds `[MenuItem]`-style
assertions that log `[DIAG] PASS/FAIL`, so they can run headless:

```bash
"/Applications/Unity/Hub/Editor/2022.3.62f2/Unity.app/Contents/MacOS/Unity" \
  -batchmode -nographics -quit \
  -projectPath "/Users/stevenwu/Documents/GitHub/Rogue Asian Fantasy" \
  -executeMethod MapgenDiagnostics.ChestWalkability \
  -logFile - 2>&1 | grep -E "\[DIAG\]|error CS"
```

| Method | Menu item | Needs |
| --- | --- | --- |
| `ChestWalkability` | `Tools/Diagnose/Opened Chest Walkability` | edit mode; builds a synthetic grid |
| `OpenRealChest` | `Tools/Diagnose/Open A Real Chest (Play mode)` | Play mode; opens a real generated chest |

Both are safe to run on the user's open scene, with one caveat: they call
`IslandManager.Rebuild`, which replaces the editor's island map until the next
generation run. Prefer Play mode for anything that touches the scene, and prefer
`OpenRealChest` over the synthetic one when Play mode is available — it exercises the
real `Chest.Open`.

**3. Driving a live editor (UnityAgentClient bridge).** An embedded package,
`Packages/com.nuskey.unity-agent-client`, runs a small HTTP server on
`http://localhost:57123`:

| Endpoint | Purpose |
| --- | --- |
| `GET /tools` | Advertised tool list. |
| `GET /editor_state` | `isPlaying`, `isPaused`, `isCompiling`, `isUpdating`, `activeScene`, `activeSceneDirty`. **Check this first.** |
| `POST /execute_method` | `{"type":"...","method":"...","timeoutMs":30000}` — runs any static method on the editor's main thread. Unity's own API works, e.g. `UnityEditor.EditorApplication.EnterPlaymode` / `ExitPlaymode`. |
| `POST /read_unity_console` | `{"maxCount":N}` — the editor's log buffer. |

Rules that keep this useful:

- **It only works while the editor's main loop is running.** When Unity is in the
  background macOS throttles it, `EditorApplication.delayCall` never fires, and requests
  time out with an honest `TIMEOUT after ...ms`. Wake it with
  `open -a "/Applications/Unity/Hub/Editor/2022.3.62f2/Unity.app"` (AppleScript
  `activate` is not enough, and `System Events` is blocked by macOS permissions).
- Unity does **not** always import external file edits while unfocused, even with
  Auto Refresh on. After editing C#, wake the editor as above and poll `GET /tools`
  or a known method name until the new code answers.
- The log buffer starts empty at each domain reload, and a domain reload drops the
  in-flight response. Make the call, then *read the console* for the result.
- `activeSceneDirty` is your guard against destroying unsaved scene work. Anything that
  opens a scene or generates into the current one is destructive: check the flag and ask
  the user first.
- Entering Play mode is the safe way to exercise generation and runtime paths: it uses
  the real code and reverts the scene on stop.

**4. What you cannot verify.** Anything needing input, physics, or visual confirmation —
movement feel, whether a shot connects, UI layout, combat feedback. Say so plainly rather
than implying you ran the game, and hand the user a short manual check list. Playing the
scene once and reading the console for exceptions is worth doing, but it is not the same
as verifying balance or feel.

Never report that a change works because it "looks correct" — and never conclude a
serialized field is empty from a filtered view of a `.unity`/`.prefab` file. Read the
block verbatim: nested class fields are indented deeper than their parent key and
list entries start with `-`, so a `^  \w` filter hides every value and makes populated
fields look empty.

## Scope discipline

- Read the call sites of anything you touch: `Grid`, `EntityManager`, `IslandManager`,
  `TurnManager`, and the `static event` channels are load-bearing contracts.
- Make the smallest change that satisfies the request. Do not refactor toward a
  preferred style or reorganize folders unless asked. There are cosmetic names worth
  leaving alone — `Assets/Scripts/Level Generator/ProceduralGeneraltionAlgorithm.cs`
  (the file name is misspelled, the class inside is not), `BrachingRooms`,
  `Assets/Scripts/Managers/levelUpUI.cs`, `Assets/Scripts/Managers/UI Manager.cs` — but
  note they are *only* cosmetic: that static class has zero scene/prefab references. What
  actually breaks assets is renaming a serialized **field** or a **GameObject** the code
  looks up by name, per contracts 1 and 6.
- `Packages/manifest.json` currently holds `feature.2d`, `ide.rider`,
  `ide.visualstudio`, `render-pipelines.universal`, `test-framework`, `textmeshpro`,
  `ugui` and 31 built-in modules. `visualscripting`, `timeline`, `ai.navigation` and
  `collab-proxy` were removed. Do not add or remove packages without asking; either
  direction forces a full reimport for the user.
- Never run `git add -A` (see the untracked tooling above).
- Do not commit. Leave changes in the working tree for review.
