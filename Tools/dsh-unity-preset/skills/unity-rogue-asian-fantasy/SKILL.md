# Rogue Asian Fantasy — project coding reference

Turn-based 2D roguelike dungeon crawler. Unity **2022.3.62f2**, URP 14, 2D feature
set, Tilemap, TextMeshPro, UGUI, and the legacy `Input` API.

Nearly all gameplay code is ~3,600 lines of plain C# under `Assets/Scripts`, in
the default `Assembly-CSharp` assembly with **no namespaces** and **no `.asmdef`**.
Only `Assets/CastVisualizer` and `Assets/TextMesh Pro` have their own assemblies,
and both are vendored third-party code.

## Do not edit these

| Path | Why |
| --- | --- |
| `*.unity`, `*.prefab`, `*.asset`, `*.controller`, `*.anim` | Unity-editor-authored YAML. Hand-editing corrupts GUID/fileID references. |
| `*.meta` | Unity owns sidecar metadata and GUIDs. Never create, edit, or delete one by hand. |
| `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/` | Generated. Gitignored scratch. |
| `*.csproj`, `*.sln` | Regenerated by Unity / IDE integration. |
| `Assets/TextMesh Pro/`, `Assets/CastVisualizer/` | Vendored packages. Treat as read-only; changes are lost on reimport. |

When a task genuinely needs scene, prefab, or inspector wiring (a new serialized
field to fill in, a list to populate, a component to add), finish the complete C#
side and then hand the user a short, explicit editor checklist. Do not attempt
the wiring yourself.

**Never rename or retype an existing serialized field** (`public` fields and
`[SerializeField]` privates) without telling the user. Their values are stored in
scenes and prefabs keyed by field name; renaming silently resets the data to
default and is very hard to notice.

## Runtime contracts

These are the shared invariants the whole game relies on. Read the call sites
before changing any of them.

### 1. The grid is terrain only; entities are separate

`Grid` (`Assets/Scripts/GameGrid/Grid.cs`) stores **terrain codes** in an
`int[width, height]`. Exactly one component owns the level grid and publishes it
as `Grid.Current`; everything else must read `Grid.Current` rather than building
or searching for its own instance.

Terrain codes in use:

| Code | Meaning | Walkable |
| --- | --- | --- |
| `0` | grass / floor / corridor | yes |
| `1` | wall | no |
| `2` | deep water | no |
| `3` | enemy | no — `Grid.detectEnemiesInALine` scans for it |
| `5` | bridge (legacy) | yes |
| `99` | chest | no |

`Grid.IsWalkableTerrain(int)` and `Grid.CellFromWorld(Vector3)` are the single
definitions of "can an entity stand here" and "which cell is this". Route new
movement, pathfinding, and generation checks through them instead of comparing
codes inline — that is how the map edge stays blocking (`Grid.OutOfBounds == 1`,
which is deliberately non-walkable).

**Entity occupancy is not in `Grid`.** `EntityManager` owns a
`Dictionary<Vector2Int, GameObject>` with a one-entity-per-cell rule, and moving
into an occupied cell is what triggers melee combat. When adding a new moving
entity you must register, move, and unregister it through `EntityManager`, or
collision and combat will silently ignore it.

Cells are derived with `Mathf.FloorToInt` on world X/Y (cell size 1, origin
`(0,0)` in practice), so keep entity positions on integer coordinates.

### 2. Turn order flows through a static event

The turn pipeline is:

1. `Controls` (player) resolves the player action and raises
   `Controls.onMoveEvent`.
2. `TurnManager.callTaketurn` receives it, alerts enemies in the player's room,
   and starts the `TakeTurns` coroutine.
3. The coroutine dequeues each `EnemyBehavior` and calls `takeTurn()` with a
   small delay, then clears `Controls.takingTurn` in a `finally` block.

`Controls.takingTurn` is the player-input lock. Anything that consumes a turn
must set it and raise `onMoveEvent` **after** the action resolves, or the player
will act again while enemies are still moving. `TurnManager` subscribes in
`Start` and unsubscribes in `OnDestroy`; new `static event` subscriptions must be
symmetric the same way, because these are static channels that survive scene
reloads and leak handlers otherwise.

### 3. Managers are scene-local singletons

`TurnManager`, `EntityManager`, `PlayerStats`, `Inventory`, `Equipments`,
`LootGen`, `CollectableMap`, and `UIManager` all expose a `static Instance` and
guard it in `Awake` with a destroy-the-duplicate check. The project-wide
convention is `public static X Instance;`, assigned in `Awake` — match that
instead of introducing a new pattern. Prefer `Grid.Current` and the existing
`Instance` accessors over `FindObjectOfType` in gameplay code.

`Manager.cs` holds `Manager.grid` / `Manager.player` but is an unfinished static
helper; prefer `Grid.Current` and `PlayerStats.Instance`.

## Coding conventions in this codebase

Match the file you are editing. This project is mid-development, so its style is
inconsistent; consistency with the surrounding file beats a global standard.

- No namespaces. `public class Foo : MonoBehaviour` at file scope.
- `MonoBehaviour` lifecycle methods are mostly `private` by convention; many are
  `void Start()` / `void Update()` with no modifier. Either is fine locally.
- Fields that designers tune are `public` or `[SerializeField] private`. Runtime
  state is `private`/`internal`.
- Coroutines (`IEnumerator` + `StartCoroutine`) drive sequenced gameplay timing
  rather than `async`/`await`, which Unity's older runtime here does not support
  well.
- Spatial queries use `Vector2Int` cells plus `Grid`/`EntityManager`, not raycasts.
- `Debug.Log` is used liberally, including in hot paths and turn loops. Keep it
  sparse in new code and prefer `Debug.LogWarning`/`LogError` for real faults.
- XML `<summary>` doc comments appear on the newer grid and entity APIs. Add them
  to new public APIs; do not retrofit the older files.
- Tabs vs spaces: files use 4 spaces. `.editorconfig` is absent, so copy the file.

## Verification

There is no unit-test suite. Verify in this order, cheapest first, and report
exactly which step you ran.

**1. Compile check (do this for every C# change).** This imports scripts and
reports compiler errors without a run loop. Use the project's exact editor:

```bash
"/Applications/Unity/Hub/Editor/2022.3.62f2/Unity.app/Contents/MacOS/Unity" \
  -batchmode -nographics -quit \
  -projectPath "/Users/stevenwu/Documents/GitHub/Rogue Asian Fantasy" \
  -logFile - 2>&1 | grep -E "error CS|Compilation failed|Scripts have compiler errors"
```

**The user usually has this project open in the Unity editor, and batchmode
cannot share it.** Two instances cannot hold the same project, so the command
aborts with `It looks like another Unity instance is running with this project
open` and exit code 134 (SIGABRT). Check for a running editor before you rely on
this step:

```bash
pgrep -fl "Unity.app/Contents/MacOS/Unity" | grep -v batchmode
```

If an editor is open, do **not** kill it to free the lock — that risks unsaved
scene work. Either fall back to step 1b, or ask the user to close it. Report that
you could not run the real compile check instead of implying you did.

If the project is free, expect roughly a minute on a cold `Library`. A clean run
prints nothing from that `grep`. Two traps: the batched editor **exits `0` even
when scripts fail to compile**, so read the log rather than the exit code; and it
rewrites `Library/`, which is gitignored. Confirm afterwards that no tracked file
changed unexpectedly:

```bash
git status --porcelain -- Assets ProjectSettings
```

**1b. Fallback when the editor is open (weaker signal).** The generated
`Assembly-CSharp.csproj` references Unity assemblies by absolute
`Library/ScriptAssemblies` path, so a Roslyn build catches syntax and type errors
against the last import — it will not see scripts Unity has not imported yet:

```bash
dotnet build "Assembly-CSharp.csproj" -nologo -v q 2>&1 | grep -E "error CS" | head -40
```

A clean build produces no `error CS` lines. `dotnet` 9 is installed system-wide.
Treat this as a weaker signal than the real editor check and say which one you ran.

**2. Logic checks that do not need Play mode.** `MapgenDiagnostics`
(`Scripts/Level Generator/Editor/MapgenDiagnostics.cs`) exposes two editor menu
items that assert the generation pipeline end to end and log a terrain census:
`Tools/Diagnose Perlin Map Walkability` and
`Tools/Diagnose Room-First Dungeon Walkability`. Both are `[MenuItem]`
`static` methods, so they can also be run headless:

```bash
"/Applications/Unity/Hub/Editor/2022.3.62f2/Unity.app/Contents/MacOS/Unity" \
  -batchmode -nographics -quit \
  -projectPath "/Users/stevenwu/Documents/GitHub/Rogue Asian Fantasy" \
  -executeMethod MapgenDiagnostics.DiagnosePerlin \
  -logFile - 2>&1 | grep -E "\[DIAG\]|error CS"
```

Use the diagnostic style it models (`[DIAG]`-tagged census and assertions logged
to the console) when you add checks for new generation code, rather than adding a
test framework.

**3. What you cannot verify.** Anything needing Play mode, input, physics, or
visual confirmation — movement feel, animation, UI layout, combat feedback. Say
so plainly rather than implying you ran the game. Hand the user a short manual
check list instead.

Never report that a change works because it "looks correct". Compile-check it,
then state the residual risk.

## Scope discipline

- Read the call sites of anything you touch: `Grid`, `EntityManager`,
  `TurnManager`, and the `static event` channels are load-bearing contracts.
- Make the smallest change that satisfies the request. Do not refactor toward a
  preferred style, rename "misspelled" public members, or reorganize folders
  unless asked — `ProceduralGeneraltionAlgorithm.cs` and similar names are
  referenced from scenes and prefabs.
- Do not add packages to `Packages/manifest.json` without asking; a dependency
  change forces a full reimport for the user.
- Do not commit. Leave changes in the working tree for review.
