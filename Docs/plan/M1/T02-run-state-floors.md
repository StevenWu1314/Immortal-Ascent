# T02 — RunState, floor progression, death and victory

**Depends on:** T01.
**GDD:** sections 3.1-3.4 (loop, run structure, floor exit, win/lose), 16.2 (systems to add), 16.3 (save

## Goal

The game becomes a run: a realm with floors, stairs that advance the floor, a boss floor that completes
the run, and death or victory returning to the menu. M1 only needs the Plains realm populated, but the
data shape must already allow three realms.

## Implementation notes

1. **Separate pure logic from MonoBehaviour.** `RunSequence` (pure, testable): holds realm index, floor
   index, floors per realm, and answers `IsBossFloor`, `AdvanceFloor()`, `IsRunComplete`,
   `Reset()`. `RunState` (MonoBehaviour singleton) owns the instance, the seed, and events; it delegates
   decisions to `RunSequence`. This is what makes M3's save/resume cheap.
2. **RealmDefinition fields (data-driven):** realm index, display name, floors in this realm, islands per
   floor, enemy pool, loot table reference, vision radius, aggro mode (`RoomWide` / `DetectionRadius`),
   hazard flags. M1 creates **only** `Plains.asset` with: 2 floors, 6-8 islands, room-wide aggro,
   unlimited vision. Desert/Tundra assets are M2 — do not create stubs.
3. **Floor advance flow:** stairs interaction → `RunState.AdvanceFloor()` → regenerate the floor in the
   same scene: clear grid/entities/chests/islands, generate the new floor, respawn the player on the
   starting island, respawn enemies and chests. Reuse the existing reset path in the generator rather than
   loading a new scene.
4. **Boss floor:** on a realm's last floor the stairs do not exist; the boss room's door opens only when
   the boss dies (T10 implements the boss; this task implements the gate flag and the run completion).
5. **Death:** keep the existing serialized death-scene field and the current behaviour (reload
   `ui.unity`, build index 0). Confirm it still works — it was recently fixed and must not regress.
6. **Victory (M1 placeholder):** when the boss dies on the final floor of the final realm, show a simple
   summary panel ("run complete") with kills / floors / time if cheap, then return to the menu. The full
   ending screen is M3.
7. **Seed:** `RunState` generates and stores one seed per run; every floor derives its layout seed from
   (run seed, floor index) so a floor is reproducible. Tests rely on this.
8. Do not add saving in this task. M1 has no persistence; the shape above is enough for M3.

## Test list (EditMode, pure)

- New run starts at realm 0, floor 0.
- `AdvanceFloor` moves within a realm and wraps into the next realm at the realm boundary.
- `IsBossFloor` is true only on the last floor of a realm.
- `IsRunComplete` only after advancing past the final realm's last floor.
- `Reset` returns to realm 0 / floor 0 and clears completion.
- Floor seed derivation is deterministic: same run seed + floor index → same layout seed; consecutive
  floors differ.
- A 3-realm sequence with floors-per-realm 2-3 covers every floor exactly once.

## Test list (PlayMode)

- Interacting with the stairs cell advances the floor: the player is back on a starting island, enemies
  exist again, and islands are rebuilt (assert via `IslandManager` and `EntityManager`).
- No stairs cell exists on a boss floor.
- Player death reloads the menu scene (assert the active scene name after the load).

## Outcome (implemented)

- `RunState` (static) + `RunSequence` (pure, testable) + `RealmDefinition` (ScriptableObject): realm and
  floor, the per-floor layout seed from `(run seed, realm, floor)`, whether the floor is a boss floor,
  and where this floor's stairs are.
- Stairs: the generator marks the `Stairs` room's centre, paints the existing bridge tile there and
  registers the cell; `E` while standing on it descends. A boss floor registers no stairs, because the
  arena ends the realm instead.
- The rebuild is driven by a static `FloorChanged` event - the generator subscribes in `Start` and
  rebuilds - so no scene object needs a reference to the run state wired in.
- Death already returned to the menu, and entering the dungeon scene calls `BeginRun`, which is what
  resets the run. No death hook was needed.
- `Tools/Content/Create Plains Realm Asset` authors `Assets/Resources/Realms/Plains.asset` (2 floors).
  The run falls back to a built-in plains definition when that folder is empty, so the menu item is
  authoring convenience rather than a prerequisite for playing.

### Deviations

- `RealmDefinition` carries only `realmIndex`, `displayName`, `floorsInRealm`. Enemy pools, loot tables,
  aggro mode and vision radius belong to the tasks that read them (T04/T06/T09); declaring them now
  would be fields nothing inspects.
- The island band stays on the generator (T01) rather than moving to the realm. With one realm there is
  nothing to vary, so T09 is the natural place to make it per-realm.
- The victory placeholder panel moves to T10: the boss does not exist yet, so the panel would be
  unreachable code. `RunState.IsComplete` is the seam T10 drives, and completing raises no
  `FloorChanged` - there is no next floor to build.

### Bugs found on the way, all pre-existing

- **The Grid outlived a generation.** `tilePlacer.clear()` clears the tilemaps but not the terrain, so
  the previous floor's room rings and chest codes stayed underneath the new floor and cut through it.
  Every descend produced isolated cells and walled-in chests (`isolated=48`, `chests=2/6`). Fixed by
  calling the new `Grid.Clear()` before a floor is placed.
- **The player was respawned per floor.** A fresh instance resets health, level and inventory, which the
  GDD carries between floors - and the player prefab carries `Equipments` and `Inventory`, whose
  duplicate-singleton guards `Destroy(gameObject)` the *whole new player* while the old one is still
  alive (`Destroy` is deferred). The generator now reuses the player: it repositions and re-registers
  the same instance.
- **`CameraFollow.LateUpdate` dereferenced before its null check**
  (`FindObjectOfType<PlayerStats>().transform` on the line *before* `if (player == null) return;`), which
  made that guard dead code and threw whenever no player existed.

### Verified

EditMode 36/36 (14 new run-state tests); PlayMode 3/3 including descending (same player instance, exactly
one player, islands rebuilt); every generation in the run reports `isolated=0` with every chest reachable.

One caveat, explained and fixed by T03: a single run reported `originWalkable=False` (spawn cell
blocked). The extra context added to that message is what identified it - a chest had been generated on
the player's spawn cell. See T03's "A T02 mystery resolved".
